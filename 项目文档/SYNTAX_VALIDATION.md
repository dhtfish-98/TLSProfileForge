# Development-only official syntax checks

The public Python API and CLI remain offline and dependency-free. These separate developer scripts download, compile and execute trusted fixed-source checkers inside a caller-selected fresh build directory. They install only into that directory's local prefix. They do not apply drafts, modify system services, initialize a PostgreSQL cluster, enter service event loops or contact a TLS server. A compiler, make, OpenSSL development files, PCRE2, Expat and Python 3.14 are needed. Linux CI additionally installs compiler/development packages, without server packages.

On macOS with existing Homebrew development libraries, run from the source tree:

```sh
python3 scripts/build_syntax_checkers.py --root validation-local/checkers --openssl-prefix /opt/homebrew/opt/openssl@3 --pcre-config /opt/homebrew/opt/pcre2/bin/pcre2-config
PYTHONPATH=src python3 scripts/check_official_syntax.py --build validation-local/checkers --openssl /opt/homebrew/opt/openssl@3/bin/openssl
```

On Linux with existing development libraries, use `--openssl-prefix /usr`, `--pcre-config /usr/bin/pcre2-config` and `--openssl /usr/bin/openssl`. The build directory must be new or empty. Optional `--archive-cache` reuses previously downloaded archives only after exact size and SHA-256 checks. All seven downloads must match [scripts/checker-sources.json](../scripts/checker-sources.json) before tar extraction or upstream build commands. These hashes record the HTTPS bytes observed locally; detached signatures were not verified. Build logs, command arguments and original licenses stay under the ignored build directory. [CHECKER_SOURCES.json](../CHECKER_SOURCES.json) identifies complete license references preserved in the source distribution. No upstream checker implementation or binary is redistributed.

| Checker | Fixed version | Execution and bounded meaning |
| --- | --- | --- |
| Nginx | 1.28.0 | Native -t, owned temporary Unix socket, no event loop; validates configuration and TLS setup exercised by -t |
| Apache HTTP Server | 2.4.67 | Native -t with locally built mod_ssl; selected configuration syntax only |
| HAProxy | 3.0.10 | Native -c check mode; selected configuration acceptance |
| PostgreSQL | 18.1 | Native -C ssl reads selected configuration and exits, without initdb; no TLS connection or complete SSL-context claim |
| Redis | 7.4.1 | Unmodified official parser validates the generated prefix before an exact deliberate unknown-directive marker; a separate test-only driver executes official TLS setup before server initialization |

Each checker runs modern and intermediate drafts. Only temporary synthetic certificate/key/CA paths and required enclosing scaffolding are substituted. The Redis scaffold additionally disables both service ports and persistence as an outside guard. Selected protocols, suites and groups are retained. The validator requires expected exit codes and marker/error messages; signal crashes, a failure unrelated to the negative control, or an absent binary cannot count as PASS. It hashes executables, observes their version commands and records platform dynamic-link listings. Linked-library listings are observations, not a proof of every provider or subsequent loader state.

Redis configuration string setters defer some TLS checks. Consequently the deliberate parser marker alone is insufficient for TLS value validation. The additional driver is a clearly marked seven-line modification to fixed `src/server.c`, documented in [scripts/redis_tls_driver.patch](../scripts/redis_tls_driver.patch). Its original and patched SHA-256 values are checked before compilation. Main has already performed the official configuration/TLS-type initialization and parsed the generated file. The added call invokes `connTypeConfigure(connectionTypeTls(), &server.tls_ctx_config, 1)`, reaching the unchanged official `tlsConfigure` and OpenSSL certificate/suite checks. Success or failure then exits before `initServer`, listener setup and the event loop. TLS, config, connection, socket and Unix-socket implementations are unchanged. This is a modified test driver, not a native Redis dry-run. The Redis driver/patch carries Redis 7.4.1's RSALv2 OR SSPLv1 terms separately from the MPL-2.0 generator; its full original license is retained.

On local macOS/OpenSSL 3.6.2, a fresh build and validator replay produced 12 PASS positive checks and 17 PASS negative controls. Negative controls include invalid protocols for every service; both Redis profiles additionally reject wholly invalid TLS 1.3 suites, malformed certificate ASN.1 and mismatched private keys; the intermediate profile rejects wholly invalid TLS 1.2 suites. Mixed unknown/valid OpenSSL suite expressions may be accepted, so controls use entirely invalid expressions. This execution evidence covers one fixed version per service and does not prove all versions in the model or complete guideline/security behavior.

The isolated official-syntax CI job builds the same archive identities and runs the same positive/negative checks, using the runner's observed development library. Source package tests and clean wheel-consumer tests remain separate gates. A configured CI job is OPEN until its exact commit has run successfully. Temporary private keys, upstream archives, binaries, sources, logs and synthetic config files stay outside Git and both package formats.

Primary invocation references: [Nginx switches](https://nginx.org/en/docs/switches.html), [Apache httpd -t](https://httpd.apache.org/docs/2.4/programs/httpd.html), [HAProxy 3.0 management](https://www.haproxy.org/download/3.0/doc/management.txt), [PostgreSQL 18 postgres -C](https://www.postgresql.org/docs/18/app-postgres.html). Redis ordering and TLS setup were checked against the fixed [server.c](https://github.com/redis/redis/blob/7.4.1/src/server.c), [config.c](https://github.com/redis/redis/blob/7.4.1/src/config.c), [connection.c](https://github.com/redis/redis/blob/7.4.1/src/connection.c) and [tls.c](https://github.com/redis/redis/blob/7.4.1/src/tls.c). Native complete Redis dry-run, actual services/handshakes, deployment security and CVP eligibility remain OPEN.
